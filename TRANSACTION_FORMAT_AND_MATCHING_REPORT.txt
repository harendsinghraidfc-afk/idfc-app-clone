┌────────────────────────────────────────────────────────────────────────────┐
│ 1. CORE PRINCIPLE - BANKING GRADE DUAL ENTRY                              │
│                                                                            │
│    RULE: Har DEBIT transaction ke liye EXACTLY EK CREDIT transaction      │
│          hona CHAHIYE, same amount + same UTR + same timestamp.           │
│          In dono ko milkar EK "MATCHED PAIR" banta hai.                    │
│                                                                            │
│    Golden Formula:  SUM(ALL DEBITS)  =  SUM(ALL CREDITS)                   │
│                    (Across entire system, always zero difference)         │
│                                                                            │
│    Exceptions: Only those marked "STANDALONE"                             │
│       → Cash Deposit at Branch (only Credit, no internal Debit)            │
│       → Salary Credit from Employer (only Credit)                          │
│       → Bank Charges / Penalty (only Debit)                                │
│       → Interest Credit (only Credit)                                      │
│    These carry a flag: standalone=true                                     │
└────────────────────────────────────────────────────────────────────────────┘

  5. MATCHING / RECONCILIATION ENGINE - STEP BY STEP ALGORITHM
================================================================================

This runs: (A) On EVERY transaction write  (B) Nightly 23:59 batch  (C) Admin button

────────────────────────────────────────────────────────────────────────
Step 1: UTR Pair Build (by_utr index)
────────────────────────────────────────────────────────────────────────
For every transaction:
  → If standalone=true  → SKIP pair match (mark RECONCILED=true, reason=STANDALONE)
  → Else:
      Look up by_utr[ txn.utr ]
        • If entry missing → create:  { debit_id:null, credit_id:null, status:"PENDING" }
        • If txn.leg = DEBIT  → by_utr[utr].debit_id  = txn.id
        • If txn.leg = CREDIT → by_utr[utr].credit_id = txn.id

────────────────────────────────────────────────────────────────────────
Step 2: Pair Match Check (Per UTR)
────────────────────────────────────────────────────────────────────────
For each UTR in by_utr:

  Case A: Both debit_id AND credit_id present
    → Load both txn objects (from two customer buckets)
    → Compare 4 rules:
        Rule 1: amounts identical (parse numbers, exact match)
        Rule 2: from_customer_id of DEBIT == to_customer_id in pair opposite? YES
        Rule 3: Both statuses != FAILED
        Rule 4: Timestamp delta < 300 seconds (5 min)

    → All 4 pass → status = "MATCHED"
                   → Mark BOTH txns: reconciled=true, reconcile_timestamp=now
    → Any fail    → status = "MISMATCH"
                   → Add to unmatched_queue with mismatch_reason
                   → Alert admin dashboard

  Case B: Only debit_id present
    → Check if txn.date older than T+0 (today)
       • No  → wait (status = UNMATCHED_DEBIT, temp)
       • Yes → push to unmatched_queue: "DEBIT WITHOUT CREDIT (UTR xxx)"
                Admin can: [Resolve to Standalone / Force pair / Reverse]

  Case C: Only credit_id present
    → Same as B → unmatched_queue: "CREDIT WITHOUT DEBIT (UTR xxx)"
                (Could be salary, cash deposit, etc.)
                Admin can: [Mark Standalone / Find pair / Reject]

────────────────────────────────────────────────────────────────────────
Step 3: Global System Consistency (Zero Sum)
────────────────────────────────────────────────────────────────────────
Sum ALL txns:
   total = Σ ( amount_num * (leg=="DEBIT" ? -1 : +1) * (status=="APPROVED" ? 1 : 0) )

Expected result after full reconcile:
   total == Σ STANDALONE TXNS only (because real pairs cancel out)

If total != expected: → CRITICAL ALERT, admin panel RED
   → Possible causes: tamper, mid-write crash, admin partial edit

────────────────────────────────────────────────────────────────────────
Step 4: Per-User Running Balance Audit
────────────────────────────────────────────────────────────────────────
For EACH customer_id:
   Calc balance_oldest_to_newest (getCalculatedBalance existing logic)
   Also cross check:
      user.availableBalance  MUST  ==  getCalculatedBalance()

   If mismatch: → Add to audit_log + auto-fix (write correct value)
                 → Admin notified "Auto-fix: User 8822334455 balance corrected"

────────────────────────────────────────────────────────────────────────

  6. FULL TRANSACTION FLOW - USER SENDS MONEY TO OTHER USER (Example)
================================================================================

User Aman (8822334455) → ₹500 → Rahul (6910097017) via UPI

Step 1   Aman opens Pay to Mobile → enters phone, amount, remarks
Step 2   Validate:
         • Phone maps to Rahul? (Lookup users.json by customerId/phone field)
         • Aman balance >= ₹500? (YES/NO → "Insufficient balance")
         • If NO → FAIL record (single, FAILED, no pair needed)
Step 3   MPIN prompt → 4 digit enter
         • auth.js compare → match pass
Step 4   System generates 1 UTR = "UPI2208202614362200001"
Step 5   Build Aman's DEBIT leg + Rahul's CREDIT leg (both objects in memory)
Step 6   Insert BOTH atomically (write localStorage in ONE operation,
         so system never sees half-written state)
Step 7   Run inline Reconcile Step 1-2 for this UTR
         → by_utr entry: both IDs present, amount match → MATCHED
         → Both txns set reconciled=true
Step 8   Recalculate Aman balance (decrease ₹500)
         Recalculate Rahul balance (increase ₹500)
         Update users.json both records
Step 9   UI shows: "Payment Successful | UTR: UPI2208xxxx" + receipt
Step 10  Aman's transactions + Rahul's transactions BOTH show new record
         (Aman sees ₹-500 red,  Rahul sees ₹+500 green)

RESULT: 2 transaction records generated → 100% Matched Pair ✓
        Global sum unaffected (₹-500 + ₹+500 = 0) ✓

  8. ADMIN REVERSAL FLOW (How to undo mistakes, keeping matching)
================================================================================

If admin needs to reverse txn_id 5001 (₹500 DEBIT Aman → Rahul):

Step 1  Admin clicks "Reverse" on 5001
Step 2  Reason popup: "Customer dispute, wrong beneficiary"
Step 3  System loads pair via utr → finds 5002 (the CREDIT in Rahul)
Step 4  Generate NEW UTR: "REV2208xxxxxx"
Step 5  Generate REVERSE pair:
         5099: DEBIT  Rahul  ₹500  reverse_of=5002
         5100: CREDIT Aman   ₹500  reverse_of=5001
Step 6  Original 5001.status = "REVERSED"
        Original 5002.status = "REVERSED"
        Original by_utr entry → "MATCHED_REVERSED"
Step 7  Reverse pair 5099/5100 → "MATCHED"
Step 8  Balances recalc: Aman +500, Rahul -500 (back to original)
Step 9  Audit log writes 2 entries

RESULT: Original pair kept intact (audit trail never lost)
        Reverse pair also matched 100%
        Net effect on all users: Zero (as if never happened)
        History is preserved, not deleted!


================================================================================
  9. TAMPER PROTECTION (Why checksum field?)
================================================================================

Every transaction write:
   payload_string = JSON string of all fields in fixed key order
   checksum = SHA256(payload_string + server_salt_from_env)
   store checksum field alongside

Every reconcile run:
   Re-compute checksum for EACH txn and compare to stored value
   MISMATCH → audit_log: "POSSIBLE TAMPER: txn 5001 checksum mismatch"
              Mark that txn ON_HOLD, block user actions until admin review

Admin cannot silently change amount without checksum invalidating.
Fix: Admin edits go through admin panel → panel updates checksum correctly,
     plus logs admin action in audit_log[] with reason.
